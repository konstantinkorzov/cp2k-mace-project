# Аудит безопасности и устойчивости протокола

Дата: 2026-11-26. Ревизия: `daddc3f` + исправления этой итерации.
Метод: чтение критичных модулей + исполняемый набор атак `test/attack_suite.py`
(13 сценариев, без CP2K).

> Это **первая итерация**. Код частично писал тот же агент, поэтому аудит не
> является независимым. Перед публичным запуском с реальной ценностью нужен
> внешний аудитор (см. §7).

## 1. Что проверялось

детальный разбор UI-логики панели, производительность CP2K.

## 2. Модель угроз (как есть)

- **Воркер не доверенный**: может врать в числах, подменять геометрию, не считать.
- **Мастер-пир не доверенный**: может прислать фальшивый блок, длинную ветку,
  битый blob, занять CPU проверками.
- **Кто угодно в сети** видит порт мастера (8000) и панель (8443).
- **Консенсус** = «полезная работа»: блок принимается только после пересчёта
  DFT от присланного wfn (дорого). PoW нет.

## 3. Найдено и исправлено в этой итерации

Все пункты подтверждены `test/attack_suite.py` (до исправления — «атака прошла»,
после — «атака отбита»).

### 3.1. Эмиссия через отрицательный выход (критично)

`chain.py:_check_txs`, `verify_chain`, `validate_tx`.

Выход `-1 000 000` + выход `1 000 050` при входе 50: сумма входов равна сумме
выходов, проверки проходят, на адрес начисляется миллион. Это прямой аналог
CVE-2010-5139 в Bitcoin.

**Исправлено:** `invalid_outputs()` — каждый выход должен быть конечным
положительным числом с непустым адресом. Проверяется в mempool, в одном блоке
и при полной проверке цепочки.

### 3.2. NaN/Infinity в суммах (критично)

`json.loads` принимает `NaN`/`Infinity`. `NaN` делает все сравнения ложными,
поэтому проверки «входы ≥ выходы» и «coinbase ≤ субсидия» молча проходили,
а баланс отравлялся.

**Исправлено:** тот же `invalid_outputs()` (`math.isfinite`).

### 3.3. Траверсал через `state_path` (высоко)

`chain.py:verify_block`, `verify_chain`.

Блок с `state_path: "../outside.bin"` ссылался на файл вне каталога элемента:
`os.path.join` выходил наружу, sha совпадал — блок принимался.

**Исправлено:** strict-формат `^blobs/[0-9a-f]{64}\.wfn$` и `state_sha256` —
64 hex. Это же закрывает запись blob по произвольному пути в
`_accept_peer_block` (имя файла строилось из `state_sha256`).

### 3.4. Траверсал и инъекция через `struct_id` (высоко)

`main.py:submit_result` (ready-путь) → `_write_chain_block`, `build_xyz_record`.

`struct_id` приходил от воркера и попадал в имя временного файла
(`f"{struct_id}.wfn"`) и в XYZ-комментарий без экранирования: `"x\n3\nEvil"`
добавлял в датасет фальшивые кадры, а `..` уводил запись за пределы каталога.

**Исправлено:** `STRUCT_ID_RE = ^[A-Za-z0-9_.:-]{1,80}$` на входе
`/submit-result` + санитайзинг в `build_xyz_record`.

### 3.5. Админ-API без токена (критично для публичного узла)

`main.py:_check_admin`: при пустом `MASTER_ADMIN_TOKEN` проверка пропускала
всех. Снаружи можно было менять `config.json` (в т.ч. `atom_diameter` —
параметр консенсуса), ставить паузу, добавлять пиров (SSRF), запускать
перекачку цепочки (CPU).

**Исправлено:** админ-API доступен **только с localhost** (HTTP-middleware);
`MASTER_ADMIN_TOKEN` больше не используется — так проще и безопаснее, внешний
доступ не открывается вообще.

### 3.6. Peer-blob без ограничений (высоко)

`main.py:_fetch_blob`: скачивал ответ целиком, без лимита размера и без
проверки формата `sha`. Пир мог отдать гигабайты (OOM) или подсунуть
`sha = "../../x"`.

**Исправлено:** `sha` — strict 64 hex; потоковое чтение с лимитом
`restart_max_mb`; `Content-Length` проверяется до чтения.

### 3.8. Float-деньги (критично для консенсуса)

Суммы были `float`: округление и порядок сложения могли разойтись между
узлами, а `NaN`/`Infinity` обходили сравнения.

**Исправлено:** деньги только целые (`int`). `COINBASE_VALUE = 50 000 000`,
`REWARD_VALUE = 25 000 000`, `TX_FEE = 100 000`. `invalid_outputs` требует
`type(value) is int` и `> 0`; все суммы (mempool, блок, цепочка, балансы,
кошелёк, панель) — целые. Старая цепочка несовместима → перенесена в
`results/Cu/legacy_float_*`, сеть стартовала с нового генезиса.

### 3.9. Заголовок блока проверялся частично (высоко)

Лишние/отсутствующие поля и типы не проверялись: блок с `n_atoms` строкой или
с добавленным полем проходил.

**Исправлено:** `validate_header` — ровно 11 полей, фиксированные типы,
`seq`/`element`/`n_atoms` сверяются с именем файла, `cp2k_params` обязан
содержать ключи `CP2K_PARAMS`. Используется в `verify_block`, `verify_chain`
и при приёме блока от пира.

### 3.10. Нет rate limit (высоко, DoS)

`/get-task` и `/submit-result` принимали неограниченный поток запросов.

**Исправлено:** не чаще раза в 5 с на воркера (`RATE_LIMIT_SEC`), ответ `429` +
`Retry-After`. Задачи считаются минутами, поэтому честный воркер не страдает.

### 3.11. Коллизия имён блоков при reorg (средне)

Имя блока строилось из `n_atoms` чужого заголовка: пир мог прислать блок с тем
же `seq` и другим `n_atoms`, создав второе имя → `verify_chain` ломался при
рестарте.

**Исправлено:** для высоты `seq` берётся консенсусный размер этапа
(`_expected_n_atoms`), чужой `n_atoms` отклоняется, существующий блок с этим
`seq` — тоже.

### 3.12. Панель без аутентификации (критично при выходе в интернет)

`0.0.0.0:8443` без входа: запуск процессов, конфиг, кошелёк.

**Исправлено:** вход по паролю (scrypt-хэш в `results/webui.db`), сессии
HttpOnly+SameSite=Strict на 12 ч, смена пароля `/password`, инвалидация сессий
после смены, лимит 5 попыток/мин на IP. Первый пароль — в
`results/webui_admin_password.txt` (600) или из `WEBUI_ADMIN_PASSWORD`.
API без сессии — `401`, страницы — редирект на `/login`.

### 3.13. Регистрация воркера без доказательства ключа (высоко)

Чужой адрес можно было «занять»: `_register_worker` узнавал `pubkey_hash`,
возвращал тот же `worker_id` и снимал задачу жертвы (DoS), а совпадение id
позволяло «валить» её задачи.

**Исправлено:** `GET /register-challenge` выдаёт одноразовый nonce, воркер
подписывает `cp2k-mace-register:<nonce>`; только подтверждённая регистрация
переиспользует id и возвращает задачи. Неподписанная — отдельная сессия.

### 3.14. Нет лимита тела запроса (высоко)

`/submit-result` принимал тело любого размера: JSON + base64 декодировались в
память до проверки `restart_max_mb`.

**Исправлено:** middleware ограничивает `POST` телом
`1.4 × restart_max_mb + 2 МБ` (ровно столько, сколько нужно для допустимого
wfn), превышение → `413` до разбора.

### 3.15. Мусорные blobs от пира (средне)

Файл состояния записывался на диск **до** проверки блока; при отказе оставался
навсегда. Пир мог забить диск неудачными блоками.

**Исправлено:** запись через `.part` + `os.replace`, удаление созданного blob,
если блок не принят.

### 3.16. Самодельная Ed25519 без векторов и проверки малых порядков (средне)

**Исправлено:** добавлены векторы RFC 8032 (3 шт., плюс негативные), отбраковка
точек малого порядка у `R` и `A`, проверка `S < q` (была). Криптография
по-прежнему своя (stdlib-only), но теперь проверяется по стандарту.

### 3.17. `atom_diameter` был в правилах приёмки (средне)

Диаметр (параметр генерации) определял `min_dist` при проверке геометрии:
мастера с разными диаметрами принимали разные структуры.

**Исправлено:** в приёмке остался только физический минимум 0.5 Å
(`MIN_ATOM_DISTANCE_ANG`); диаметр влияет на генерацию, остался в админ-API и
пишется в `dft.json` для воспроизводимости.

### 3.18. Мемпул без лимита и без выбора по комиссии (высоко)

Мемпул рос безгранично, а `_save_mempool` перезаписывал файл на каждый submit
(O(n²) по диску). В блок попадали все tx в порядке вставки — комиссия ни на что
не влияла.

**Исправлено (как в Bitcoin):** лимит `MEMPOOL_MAX_TX = 10 000`; при заполнении
вытесняется самая дешёвая tx, новая принимается только если дороже; конфликт
заменяется только более дорогой tx; в блок идут до `MAX_TXS_PER_BLOCK = 2000`
переводов по убыванию комиссии, остальные ждут; запись на диск — с дебаунсом
2 с и принудительным flush на выходе.

### 3.19. Перезапись истории без работы (критично)

Блоки связывались хэшем zip и не были привязаны к содержимому: мастер мог
выкинуть транзакции из старых блоков, пересчитать zip-хэши и получить
«валидную» цепочку без единого DFT. Подпись мастера не помогает — он же её и
переставит.

**Исправлено (протокол v2):**
- `block_id` — канонический хэш заголовка, включая `tx_root` (меркл-корень
  транзакций), `state_sha256` (wfn), `dft_sha256` и `prev_id`;
- геометрия блока N: `seed = H(prev_id(N-1) ‖ nonce)`, из неё детерминированно
  строится структура (`geom_version` в заголовке);
- приёмка регенерирует геометрию из `prev_id+nonce` и требует совпадения;
- правка блока N ломает геометрию N+1, значит старый wfn невалиден и нужен
  новый DFT; перепись K блоков = K прогонов.

Атака закреплена тестом `test_rewrite_history_needs_work`: подмена dft,
пересчёт `block_id`/`prev_id` без нового расчёта → отказ «геометрия не следует
из seed».

### 3.7. Зрелость coinbase не была правилом консенсуса (средне)

`available_utxos`/`validate_tx` учитывали `coinbase_confirmations` из конфига,
а `verify_chain` не проверял зрелость вообще.

**Исправлено частично:** введена константа `COINBASE_MATURITY = 1`,
проверяется в mempool, в одном блоке и в цепочке. Значение 1 сохраняет
совместимость; **для продакшена рекомендуется 6+** (см. §6, P1) — это bump
протокола.

## 4. Найдено, но не исправлено (план)

### P0 — до публичного запуска

1. **CPU-DoS через догон цепочки.** `/chain/announce` (без auth) и пир могут
   заставить мастера проверять блок за блоком (каждый — прогон CP2K).
   *Фикс:* бюджет проверок в минуту, глубина догона, карантин пира.

### P1 — устойчивость и «не хуже Bitcoin»

3. **Подпись блока мастером** — только атрибуция («кто сделал»); защита от
   перезаписи теперь даётся привязкой `seed(prev_id)`, а не подписью.
   *Вердикт:* P2, по желанию (репутация/атрибуция датасета).
4. **Зрелость coinbase = 1.** *Фикс:* поднять до 6–100, обновить тесты и
   зафиксировать в `docs/WHITEPAPER.md` как правило консенсуса.
5. **Лимит на распаковку блока** (zip-bomb): `read_block` читает записи в
   память без ограничения. *Фикс:* проверять `ZipInfo.file_size` до чтения.

### P2

12. Мастер-API без TLS (пароли/admin-токен по сети — открытым текстом).
13. `cp2k_cmd` из конфига (инъекция при доступе к админке), `verbose_cp2k`.
14. Пароли по умолчанию `root`/`master`/`worker` в `run.sh` и панели.
15. `/admin/sync` и `verify_chain` — синхронные тяжёлые операции в потоке
    запроса.

## 5. Что уже сделано правильно

- **txid** считается по телу без подписей; подпись — по txid, поэтому подмена
  суммы/адреса после подписи не проходит.
- **Двойная трата в одном блоке** и повторный вход отклоняются.
- **coinbase ≤ 50 + комиссии блока**, лишняя эмиссия невозможна.
- **Цепочка блоков** проверяется по `prev_sha256`, seq, имени файла, blob-sha.
- **Пир обязан пересчитать DFT** от присланного wfn, иначе блок не принимается;
  числа в `dft.json` сверяются с пересчётом (энергия/gap/магнитный момент/диполь).
- **Геометрия в шаблонном режиме** сверяется до DFT (`_same_geometry`).
- **Wallet**: scrypt + encrypt-then-MAC, приватные ключи в базе зашифрованы,
  пароль не хранится.
- **Задачи**: heartbeat/lease, уникальные `struct_id`, `geometry_policy` в блоке.
- **Строгая схема заголовка**, целые деньги, rate limit задач, канонические
  имена блоков, вход в панель с scrypt-хэшем и сменой пароля.

## 6. «Не хуже первых версий Bitcoin» — где мы сейчас

| Свойство | Bitcoin 0.1–0.3 | Здесь |
|---|---|---|
| Деньги | 8-байтные целые (сатоши) | **целые монеты**, без дробей |
| Защита от эмиссии через отрицательные суммы | **баг до 2010** | исправлено |
| Зрелость coinbase | 100 блоков | 1 блок (зафиксировано) |
| Двойная трата | запрещена | запрещена |
| Подпись транзакций | ECDSA | Ed25519 (своя реализация) |
| Защита от подделки блоков | PoW + проверка | DFT-перепроверка (дорого) |
| Sybil / 51% | хешрейт | стоимость CP2K-пересчёта |
| Лимиты/DoS | частично | rate limit задач, лимит тела, мемпул по комиссии |
| Подпись блока | PoW | нет |

Вывод: по **правилам денег** после исправлений мы не хуже раннего Bitcoin
(и лучше — по отрицательным суммам). По **устойчивости к DoS и подмене
инфраструктуры** — хуже: нет лимитов, нет подписи блока, панель без auth.

## 7. Нужен ли независимый аудитор

Да, перед публичным запуском с реальной ценностью — по трём причинам:

1. Я (модель) писал значительную часть этого кода: систематическая слепота
   к собственным решениям.
2. Консенсус и криптография (своя Ed25519, scrypt-параметры, формат блоков)
   требуют взгляда «снаружи» и формального анализа.
3. Публичный образ и открытый протокол привлекают атакующих, которых не
   эмулирует ни один локальный набор тестов.

**Что передать аудитору:** этот файл, `test/attack_suite.py`,
`test/test_zero_trust.py`, `docs/WHITEPAPER.md`, `Dockerfile`, и отдельно —
список P0/P1. **Ориентир по объёму:** 5–8 человеко-дней на консенсус+крипто,
2–3 — на HTTP/панель. Формат — «threat model → findings → patch review».

До этого: закрыть P0, поднять `COINBASE_MATURITY`, выключить внешний доступ к
панели, задать `MASTER_ADMIN_TOKEN`.
